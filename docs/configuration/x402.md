## 💸 x402 top-ups

Top-ups through x402 are **optional** and require [💰 Billing](./billing.md). Without an `x402` section in the [static configuration](./README.md#static-configuration), the ledger is only credited by administrators (`billing manual-refund`) and the bot never talks to a payment service.

With the section present, users pay into a room's balance with USDT (TRC-20) on TRON:

1. When a room cannot afford the next reply (or a user runs `!bai topup`), the bot asks the payment sidecar for a payment request and sends it to the room as a [`cc.chums.x402_request` event](../matrix-events.md). The Chums client renders it as a payment widget; other clients see a plain text message.
2. The user signs the payment in their wallet and the client submits it through the sidecar.
3. Once the payment settles on-chain, the sidecar notifies the bot on an internal HTTP endpoint. The bot credits the room in the ledger and confirms in the room, with a [`cc.chums.x402_topup_confirmed` event](../matrix-events.md) and a text message.

The x402 wire format, the facilitator and the on-chain part live in the payment sidecar, a separate service in the [`x402-sidecar/`](../../x402-sidecar/README.md) directory of this repository. The bot only exchanges JSON with it over HTTP.


### Configuration

```yaml
x402:
  sidecar_url: http://127.0.0.1:8402
  internal_secret: "<the same secret as X402_INTERNAL_SECRET of the sidecar>"
  internal_bind: 127.0.0.1
  internal_port: 9000
  allow_non_loopback_bind: false
```

| Key | Meaning |
|---|---|
| `sidecar_url` | Base URL of the payment sidecar. Required. |
| `internal_secret` | Secret shared with the sidecar. The sidecar signs each settlement notification with it (HMAC-SHA256), and the bot rejects notifications with a bad signature. Required. |
| `internal_bind`, `internal_port` | Where the bot listens for the sidecar's settlement notifications (`POST /internal/x402-settled`). Defaults to `127.0.0.1:9000`. The sidecar's `BOT_X402_NOTIFY_URL` must point here. |
| `allow_non_loopback_bind` | The bot refuses to listen on a non-loopback address unless this is `true`. Needed when the sidecar runs in another container or host. The endpoint is then protected by the HMAC only, so firewall it to the sidecar. Defaults to `false`. |

Every key can be overridden with an environment variable, following the usual naming rule (`x402.sidecar_url` → `BAIBOT_X402_SIDECAR_URL`). Setting any `BAIBOT_X402_*` variable enables the section even when the configuration file has no `x402` section.

Startup fails when the section is present but incomplete, when `billing` is missing, or when `internal_bind` is not a loopback address and `allow_non_loopback_bind` is off.

The bounds of a single top-up (`min_topup_usd`, `max_topup_usd`) are part of the [billing configuration](./billing.md#configuration).


### Chat command

- `!bai topup` — asks for a top-up of `billing.min_topup_usd`.
- `!bai topup <amount_usd>` — asks for a top-up of the given amount, which must lie within `[min_topup_usd, max_topup_usd]`.

Available to everyone in the room, like `balance`. Without an `x402` section, the command replies that top-ups from chat are not available.


### Security notes

- The settlement endpoint credits money, so it is only as safe as the shared secret and the network path to it. Keep it on loopback or on a private network between the bot and the sidecar.
- A settlement is credited at most once per `payment_id`. Repeated notifications (sidecar retries, races) are answered with HTTP 409 and change nothing.
- The bot never handles keys or funds. The receiving wallet, the token contract and the network are configured in the sidecar and forwarded to the client verbatim.
